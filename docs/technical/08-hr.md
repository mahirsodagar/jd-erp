# 8 — HR (`employees`, `leaves`, `relieving`, `tasks`)

Mounted at `/api/employees/`, `/api/leaves/`, `/api/hr/relieving/`,
`/api/tasks/`. Frontend under `src/pages/employees/`, `src/pages/leaves/`,
`src/pages/hr/`, `src/pages/tasks/`.

Two older scope documents remain accurate and add detail:
`docs/scope_employee.md` and `docs/scope_leave.md`. The frontend repo carries
`LEAVE_MODULE_DOCUMENTATION.md` for the leave screens.

## 8.1 `employees` — the employee master

### Models

**`Department`** and **`Designation`** — small reference lists sharing one
permission set (`employees.master.*`). `Designation.role` is important: when
set, provisioning an employee's portal account attaches **that role** to the
new `User`.

**`Employee`** — the full HR record.

| Group | Fields |
|---|---|
| Identity | `emp_code` (unique, `^[A-Z0-9-]+$`, generated as `{CAMPUS}-{YYYY}-{seq:04d}`), first/middle/family name, `dob`, `nationality`, `blood_group`, `gender`, `qualification` |
| Employment | `employment_type` (full/part time), `employment_category` (contract/professional), `date_of_appointment`, `date_of_joining`, `designation`, `department`, `campus`, `institute` |
| Reporting | `reporting_manager_1..4`, self-FKs. **L1 is required by HR policy** for everyone except the top-level director; the serializer enforces non-null on normal creates. L1 is `PROTECT`, L2–L4 are `SET_NULL` |
| Address | current + permanent, each with `address`, `city`, `state` |
| Contact | `mobile_primary`, `mobile_alternate`, `email_primary` (unique), `email_alternate` |
| Media | `photo`, `qr_code` |
| Status | `status` (0 ACTIVE / 1 INACTIVE), `is_deleted`, `deleted_at` |
| Portal | `user_account` (1:1 → `User`), `portal_temp_password` |

**Soft delete** — this is the only model in the system that uses it.
`Employee.objects` filters `is_deleted=False`; `Employee.all_objects` does not.
Sequence generation deliberately scans `all_objects` so a deleted employee's
code is never reused.

**`EmployeeDocument`** — offer letters, ID proofs, certificates. Validated by
`services.validate_document` (PDF and common images only) and carrying its own
permission keys (`employees.document.*`) rather than riding on
`employees.employee.edit`.

### Services (`services.py`)

Pure-Python image work (Pillow + qrcode), no system libraries required:

- `generate_emp_code(campus_code, year)` — prefix-scan sequence.
- `validate_photo` / `make_thumbnail` — JPEG/PNG only, ≤ 2 MB, thumbnailed to
  300×300.
- `make_qr_image` / `regenerate_qr` — payload `emp:{id}:{emp_code}`.
- `render_id_card(employee)` — a CR-80 card at 300 DPI (1010×636 px) as PNG.
  Font lookup falls back across DejaVu → Arial → Helvetica → Pillow's default,
  so a host with no TrueType fonts still renders (just uglier).

### Endpoints

| Path | Notes |
|---|---|
| `GET/POST /api/employees/` | Campus-scoped list |
| `GET/PATCH/DELETE /api/employees/<id>/` | DELETE soft-deletes |
| `POST /api/employees/<id>/activate/` · `/deactivate/` | Status flip |
| `GET/POST /api/employees/<id>/documents/`, `DELETE .../<doc_id>/` | |
| `GET /api/employees/<id>/id-card.png` · `/qr.png` | Rendered images |
| `POST /api/employees/<id>/portal-account/` | Provision the login |
| `GET/POST /api/employees/departments/`, `/designations/` + detail | |

### Access control

`EmployeeAccessPolicy` + `filter_visible`:

- `employees.employee.view` is required to reach the module.
- Lists are scoped to `user.campuses` **plus the caller's own record**, unless
  they hold `employees.employee.view_all_campuses`.
- An employee can always read their own record.

Keys: `.view`, `.view_all_campuses`, `.view_sensitive` (personal/family/address),
`.manage_deleted`, `.create`, `.add_in_any_campus`, `.edit`, `.change_status`,
`.delete`, `.provision_portal`; plus `employees.master.*` and
`employees.document.*`.

### Provisioning a portal account

`POST /api/employees/<id>/portal-account/` creates a `User`, links it, attaches
the `Designation.role` if set (otherwise the seeded `Faculty` role), and
mirrors the generated password to `Employee.portal_temp_password`.
`manage.py backfill_employee_users` does the same in bulk for employees created
before the feature existed.

## 8.2 `leaves` — employee leave and comp-off

> **Read this first.** The leave module was deliberately rewritten to match the
> legacy PHP system exactly. **Withdraw, cancel and holiday-calendar features
> were dropped on purpose** and there are no permission keys for them. Do not
> re-add them without an explicit request — a previous attempt was reverted.

### Models

| Model | Notes |
|---|---|
| `LeaveType` | `code`, `name`, `category` (LEAVE / ON_DUTY), `half_day_allowed` |
| `LeaveAllocation` | Grant of days for `(employee, leave_type, start_date, end_date)`, unique on that tuple |
| `LeaveApplication` | `from_date`, `to_date`, `from_session`, `count`, `reason`, `manager_email` (**snapshotted at apply time so RM changes never reroute a pending request**), `cc_emails`, `status` (1 PENDING / 2 APPROVED / 3 REJECTED), `approver_remarks`, `approved_by` |
| `CompOffApplication` | `worked_date`, `worked_session_1/2`, `count`, `reason`, same status enum |
| `EmailDispatchLog` | This module's **own** email log — separate from `notifications.NotificationDispatchLog` |

`from_session`: `1` = AM (half), `2` = full day, `3`/`4` = permission slots
(half).

### Day counting (`services/day_count.py`)

Legacy behaviour, ported verbatim: **plain calendar days, inclusive of both
endpoints, with no weekend or holiday netting.** A single-day request is 0.5
for sessions 1/3/4 and 1.0 for session 2; a multi-day request is
`(to − from).days + 1`.

> The setting `LEAVES_EXCLUDE_HOLIDAYS_AND_WEEKENDS` still exists in
> `settings.py` (default `True`) but the current `count_days` does not read it.
> It is a leftover from the pre-port implementation. Do not rely on it.

### Balances (`services/balance.py`)

Two different models coexist, both intentional:

1. **Lifetime balances** (`compute_balance`, `all_balances`) — mirrors
   `leave_balances.php`: `granted` (Σ all allocations) − `availed` (Σ approved
   applications), with `pending` reported separately. Comp-off is a derived
   pool: `earned` (approved comp-off requests) − `used` (approved COMP_OFF
   leaves). ON_DUTY types are unlimited and return nulls for parity only.
2. **The Apply dashboard** (`cl_dashboard`) — mirrors `leave_apply.php`:
   Casual Leave accrues 1 per month over a **hard-coded leave year of
   1 Jun 2025 – 31 May 2026** (`LEAVE_YEAR_START` / `LEAVE_YEAR_END`,
   `CL_PER_YEAR = 12`). CL balance = `12 − (number of distinct months in which
   a CL was approved)`.

> ⚠ **Maintenance item.** The leave-year constants are hard-coded module
> constants. They must be updated each academic year, or the Apply dashboard
> will report against a stale window. This is the single most likely
> "why are the numbers wrong" question after handover.

### Approval rules

**Being the applicant's reporting manager authorises a decision with no
permission key at all.** The keys widen that:

| Key | Effect |
|---|---|
| `leaves.application.view_all` | See everyone's applications |
| `leaves.application.approve_any` / `.reject_any` | Decide outside your own team. Approve and reject are separate |
| `leaves.compoff.view_all` / `.approve_any` / `.reject_any` | Same for comp-off |
| `leaves.allocation.view` / `.view_all_campuses` / `.add` / `.delete` | Allocations (delete only while unconsumed) |
| `leaves.type.view/add/edit/delete` | Leave types |
| `leaves.report.view` / `.view_all` / `.delete` | The report page |

Applying is always for yourself — the on-behalf-of path was removed and has no
key.

### Endpoints

`types/`, `allocations/` (+ `/bulk/`), `applications/` (+ `/balances/`,
`/dashboard/`, `/<id>/decision/`), `comp-off/` (+ `/balance/`,
`/<id>/decision/`), `reports/summary/`.

### Notifications

`services/notifications.py` writes to **`EmailDispatchLog`**, not to the
notifications queue. HR is CC'd via `settings.LEAVES_HR_INBOX`
(default `leave@jdinstitute.edu.in`).

The employee-facing triggers `leaves.application_employee.email` and
`leaves.application_status_employee.email` route through **SMTP on
`jdinstitute.edu.in`** and are listed in `SMTP_INTERNAL_TEMPLATE_KEYS` — they
must never be added to `MSG91_EMAIL_TEMPLATES`. Student leave status
(`leaves.application_status_student.email`) does go through MSG91.

## 8.3 `relieving` — the exit workflow

### Models

**`RelievingApplication`** — `employee`, `reason`,
`last_working_date_requested`, `last_working_date_approved` (set by HR at
finalize), `status`, rejection trail, `relieving_letter_no`,
`experience_letter_no`, `finalized_at/by`.

A partial unique constraint allows **only one open application per employee**
(open = SUBMITTED, IN_REVIEW, APPROVED).

**`RelievingApproval`** — one row per level 1–4, unique on
`(application, level)`. The approver is **snapshotted from
`employee.reporting_manager_<level>` at submission time**, so later org-chart
changes never reroute a pending application. Levels with no configured manager
are created as `SKIPPED`.

### Flow

```
submit()      → creates the application + 4 approval rows
              → errors if reporting_manager_1 is not set
decide()      → per level, approve or reject
              → a rejection stamps rejected_at_level + rejection_reason
finalize()    → HR only; sets last_working_date_approved,
                stamps REL-{INSTITUTE}-{YYYY}-{seq} and
                EXP-{INSTITUTE}-{YYYY}-{seq}, status → COMPLETED
withdraw()    → employee pulls the application
```

Letters are rendered on demand by `letters.py` (fpdf2) at
`/<id>/relieving-letter.pdf` and `/<id>/experience-letter.pdf`. Like every
other PDF here, they are not stored.

### Permissions

| Key | Effect |
|---|---|
| `hr.relieving.submit_for_others` | Submit on someone's behalf |
| `hr.relieving.view_all` | See all applications |
| `hr.relieving.finalize` | HR finalize + letter generation |
| `hr.relieving.override` | Skip approval levels |

Deciding your own level needs no key — you are the snapshotted approver.

Email triggers (`hr.relieving.application.email`,
`.application_rejected.email`, `.letter.email`, `.experience_letter.email`) all
route to the `HR` domain (`jdinstitute.edu.in`) over SMTP, and may CC the
`OPERATIONS_INBOX` / `PRINCIPAL_INBOX` / `VICE_PRINCIPAL_INBOX` /
`ACADEMIC_MANAGER_INBOX` addresses when those env vars are set.

> **Known gap.** These endpoints exist and carry permission keys, but there is
> **no dedicated frontend page for HR Relieving beyond
> `src/pages/hr/RelievingPage.tsx`** — some of the finer actions are only
> reachable through the API. Building out the remaining screens is tracked as
> a backlog item.

## 8.4 `tasks` — lightweight task assignment

`Task` mirrors the legacy `task_master`: `name`, `description`, `end_date`,
`assignee` (→ `User`), `assignee_remarks`, `status` (0 PENDING / 1 COMPLETED),
`completed_at`, `created_by`. A unique constraint on `(name, assignee)` mirrors
PHP's "Task Name Already Submitted" guard.

**Tasks are self-service and need no permission**: anyone can create one,
assign it, see the tasks they created or were assigned, edit their own fields,
and complete what is assigned to them. Only two keys exist:

| Key | Effect |
|---|---|
| `tasks.view_all` | The Tasks Report — every user's tasks |
| `tasks.delete_any` | Delete someone else's task |

Endpoints: `GET/POST /api/tasks/`, `GET/PATCH/DELETE /api/tasks/<id>/`,
`POST /api/tasks/<id>/complete/`.

Notifications `tasks.assigned.email` and `tasks.completed.email` are internal
SMTP triggers.

## 8.5 Change impact

| If you change… | Effect |
|---|---|
| `Employee.reporting_manager_1` | **Does not** reroute pending leave (uses the snapshotted `manager_email`) or pending relieving (uses snapshotted `RelievingApproval.approver`). It does affect *new* submissions |
| `Designation.role` | Only applied at provisioning time — existing portal accounts keep their current roles |
| Soft-deleting an employee | They vanish from lists but `emp_code` stays reserved; leave, relieving, schedule slots and reports still reference them (all `PROTECT`) |
| `LEAVE_YEAR_START` / `_END` | The Apply dashboard's CL accrual window. Must be updated yearly |
| `LeaveType.code` | `COMP_OFF` and `CASUAL` are matched **by code** in `balance.py`. Renaming either silently breaks comp-off and CL balances |
| Adding a leave-related email template to `MSG91_EMAIL_TEMPLATES` | Sends internal staff mail from the external marketing domain. The dispatcher logs a warning; `SMTP_INTERNAL_TEMPLATE_KEYS` exists to catch this |
| `Employee.campus` | Changes who can see the employee (campus scoping) |
