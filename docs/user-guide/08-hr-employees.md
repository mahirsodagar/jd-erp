# 8 — HR & Employees

For the HR team. Menu group: **HR**.

---

## 8.1 Adding an employee

**HR → New Employee.**

### What you will need

| Section | Details |
|---|---|
| **Identity** | First, middle and family name, date of birth, gender, nationality, blood group, qualification |
| **Employment** | Full-time or part-time; contract or professional; date of appointment; date of joining |
| **Placement** | Designation, department, campus, institute |
| **Reporting** | Up to four levels of reporting manager |
| **Address** | Current and permanent, each with city and state |
| **Contact** | Primary and alternate mobile, primary and alternate email |
| **Photo** | JPEG or PNG, up to 2 MB |

### Two rules to know

**The first reporting manager is required.** Every employee must have one — the
only exception is the top-level director, who has nobody to report to. This is
not bureaucracy: leave approvals and the exit workflow are routed through it.
An employee without one cannot apply for relieving at all.

**The employee code is generated for you** as `<campus>-<year>-<number>`. You
cannot set it, and it is never reused — even after someone leaves.

**Email addresses must be unique.** Two employees cannot share a primary email.

## 8.2 The employee record

Opening an employee shows their full record. Personal, family and address
details sit behind a separate permission from the basic record.

Everyone can always see **their own** record, whatever their permissions.

Otherwise you see employees at **your** campuses, unless you have been granted
cross-campus access.

## 8.3 Documents

Attach supporting files to an employee — offer letters, ID proof, degree
certificates, contracts. Give each a clear name so the list stays readable.

Only PDFs and common image formats are accepted, and the system checks the
actual file contents rather than the file name.

Uploading, viewing and deleting documents are separate permissions from editing
the employee, so a colleague can be given document access without full edit
rights.

## 8.4 ID cards and QR codes

Each employee has a **QR code** and a printable **ID card**, both generated by
the system.

- The QR code identifies the employee.
- The ID card is produced at card size and print quality — download and print
  it directly.

Both regenerate from the current record, so update the photo or details first,
then print.

## 8.5 Giving an employee their login

Use **Create portal account** on the employee's record.

This creates their username and password, and gives them a starting set of
access rights:

- If their **designation has a default role** attached, they get that role.
- Otherwise they get the baseline **Faculty** role, which allows them to see
  their own timetable, attendance and tests, apply for leave, use tasks, fill
  their daily report and their self-appraisal, and fill any form addressed to
  their role.

Anything beyond that is granted afterwards from **Admin → Users**.

The generated password is saved so you can share it again without another
reset. It clears itself once the employee logs in or changes their password.

> Setting a default role on a designation only affects **new** portal accounts.
> Existing accounts keep the roles they already have.

## 8.6 Departments and designations

**HR → Departments** and **HR → Designations**.

Both are simple reference lists, and both are managed by the same permission.

Designations carry one extra setting: a **default role**, used when
provisioning portal accounts (§8.5). Set this thoughtfully — it determines what
a new joiner can see on their first day.

Deactivating a department or designation hides it from new selections; existing
employees keep theirs.

## 8.7 Activating, deactivating and removing

Three different things:

| Action | Effect |
|---|---|
| **Deactivate** | Marks the employee inactive. They stay in the system with all their history |
| **Activate** | Reverses it |
| **Delete** | A *soft* delete — the record is hidden but nothing is destroyed, and the employee code stays reserved |

Nothing here removes an employee's history. Their leave records, teaching
history, reports and approvals all remain intact and attributable.

If someone has left the institute, the proper route is the relieving workflow
(§8.8), not a delete.

## 8.8 Relieving — the exit workflow

**HR → Relieving.**

**This page needs no permission.** You see your own applications and any you
must approve. The see-all permission widens it to every application.

### The steps

**1. The application is submitted.** By the employee, or by HR on their behalf
(a separate permission). It records the reason and the requested last working
date.

At this moment the system **captures the employee's four reporting managers**
onto the application. Levels with no manager configured are marked as skipped.

> Because the approvers are captured at submission, **changing someone's
> reporting manager afterwards does not reroute an application already in
> progress.** New applications use the new manager.

**2. Each manager approves or rejects**, with remarks, at their level.
A rejection records which level rejected it and why.

**3. HR finalises it.** HR sets the **approved** last working date — which may
differ from the requested one — and the application is completed.

At finalisation the system stamps two document numbers: one for the relieving
letter and one for the experience letter.

**4. Letters are generated.** Both the relieving letter and the experience
letter can be downloaded as PDFs, produced fresh from the record.

### Other things to know

- **An employee can only have one open application at a time.**
- The employee can **withdraw** their application while it is open.
- Someone with the override permission can skip approval levels where the
  normal chain cannot proceed.
- Notification emails go to the employee and, where configured, to the
  Operations, Principal, Vice-Principal and Academic Manager mailboxes.

> The relieving screens are still being built out. Some of the finer actions
> may not yet have a button — if you cannot find one, ask your technical team.

## 8.9 What your actions affect

| When you… | This happens elsewhere |
|---|---|
| Set an employee's first reporting manager | Determines who approves their **future** leave and relieving requests |
| Change a reporting manager | Requests already in progress keep the original approver |
| Create a portal account | The employee can log in immediately with the baseline access |
| Deactivate an employee | They stop appearing in active lists; their history stays intact |
| Finalise a relieving application | Letter numbers are stamped and the letters become available |
| Change a campus | Changes which colleagues can see that employee |
